# Solar Plant Performance Analysis (Python + SQL)

![Dashboard](images/dashboard.png)

> **Note on data:** all data in this project is **simulated**. It is a SCADA-style dataset generated by `generate_data.py` (fixed seed, fully reproducible), not data from any real plant or employer. The project demonstrates the analysis workflow I use on real solar O&M data.

## Business question
A 3 MWp solar plant has 12 inverters. Which inverters are underperforming, how much energy is being lost, and is the loss caused by downtime or by units that are running but producing less?

## Dataset
- 12 inverters x 250 kWp, daily data for calendar year 2025 (4,380 rows)
- Columns: irradiation, module temperature, DC voltage (avg / max), AC energy, downtime hours, availability, alarm count, main alarm type
- Realistic noise: temperature losses, monsoon cloud cover, soiling and cleaning cycles, grid trips, communication gaps (10 missing energy readings)
- Issues were injected into the data and documented at the top of `generate_data.py`. The SQL analysis never uses that information; it has to find them from the data.

## Method
1. **Data quality checks** in SQL: row counts, missing readings, duplicate keys, negative values
2. **Performance ratio (PR)** = AC energy / (DC capacity x irradiation), so results are comparable across sunny and cloudy days
3. **Fleet benchmark** = median PR of all inverters for each day (window functions), robust to a few faulty units
4. **Inverter ranking**: annual PR gap vs the fleet median, flagged WATCH (>1% below) or ACTION (>3% below)
5. **Loss split**: energy shortfall vs the benchmark, separated into *downtime* (unit off) and *underperformance* (unit on, lower output)
6. **Alarm analysis** and **underperforming-day counts** to explain the causes
7. **Weekly deviation heatmap** to see when each problem started and stopped

## Key findings (from this simulated dataset)
| Metric | Result |
|---|---|
| Plant PR | 80.3% (1,128 kWh/kWp, 3,377 MWh generated) |
| Best / worst month | Dec 84.4% / Jun 76.3% (module temperature averages about 55 C in June) |
| Average availability | 99.7%, 290 alarms |
| Estimated energy shortfall vs median inverter | about 39 MWh, roughly Rs 1.2 lakh at an assumed Rs 3.00/kWh |

- **INV-04: 6.5% below the fleet median (ACTION).** Below 95% of the fleet median on 207 running days, from 15 Mar to 10 Oct, then back to normal. This is a persistent step-change that looks like a string-level fault. It accounts for about 19 MWh, the largest single loss.
- **INV-09: 3.4% below the median (ACTION).** A repeating saw-tooth pattern in the heatmap: output drops between cleanings and recovers after cleaning or rain. This points to a soiling problem, so a more frequent cleaning schedule for that block is worth testing. About 10 MWh lost.
- **INV-11: outage.** 6 consecutive days down in July (60 downtime hours, about 5.6 MWh); almost all of its loss is downtime, not underperformance.
- **INV-02: repeated DC over-voltage trips.** 14 trip days, 26 downtime hours and 68 alarms, with small energy impact but a recurring reliability issue.
- **INV-10: 1.1% below the median (WATCH).** No distinct event found; likely normal unit-to-unit variation, so keep monitoring.

## Suggested actions
1. Inspect the strings on INV-04 (resolved in the data after 10 Oct, so confirm the repair).
2. Trial a shorter cleaning cycle for INV-09 and compare PR before/after.
3. Review the inverter fault log and spares plan for INV-11.
4. Check DC string voltage levels and the overvoltage settings on INV-02.

## Tools
Python (pandas, numpy, matplotlib), SQL (SQLite, CTEs, window functions, views)

## Project structure
```
generate_data.py        creates data/solar_scada_daily.csv (simulated, seed 42)

make_dashboard.py       builds images/dashboard.png and the four individual charts
sql/queries.sql         all SQL (setup views + 8 analysis queries)
data/  outputs/  images/
```

```bash
python generate_data.py

```

## Assumptions and limitations
- Simulated data: the numbers illustrate the method and do not describe any real plant.
- The Rs 3.00/kWh tariff is an assumption used only to put a rupee value on the shortfall.
- Availability is measured against a 10-hour daylight window.
- The shortfall is measured against the median inverter, not against a design-model (PVsyst) expectation.
- Daily data hides intraday issues such as clipping and short voltage dips.
